# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- В работе использована небольшая синтетическая база знаний по **pandas**: 10 основных документов и 3 документа для обновления базы.
- Документы были загружены из папки `data/raw/`, а дополнительные материалы для update — из `data/update/`.
- Для подготовки данных был реализован простой воспроизводимый чанкинг по символам с overlap.
- Векторизация текстовых фрагментов выполнялась с помощью **TF-IDF**, после чего по векторам строился индекс **FAISS** для top-k retrieval.
- Базовая проверка retrieval показала, что на контрольном наборе запросов система стабильно извлекает ожидаемые источники.
- После обновления базы знаний retrieval начал корректно находить документы по новым темам: **pivot tables**, **rolling windows** и **categorical data**.
- Для генерации ответа был собран простой **mini-RAG**: top-k чанки объединялись в контекст, после чего формировался extractive-ответ по наиболее релевантным предложениям.
- Источники вместе с ответом возвращались явно, что делает результат прозрачным и удобным для анализа.

  Выбранная база знаний является достаточно компактной, но тематически целостной: все документы относятся к экосистеме pandas и типовым операциям работы с табличными данными. Это удобно для retrieval-задачи, потому что по таким текстам легко формулировать короткие фактические вопросы, а ожидаемые релевантные источники понятны заранее. Такой набор также подходит для mini-RAG, потому что retrieved-фрагменты можно напрямую использовать как контекст для ответа.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- Какая embedding-модель или способ векторизации использовались: `TfidfVectorizer` из `sklearn`
- Какая метрика сходства использовалась: cosine-like similarity через `inner product` по L2-нормализованным векторам
- Какой индекс `FAISS` использовался: `faiss.IndexFlatIP`
- Какой `top_k` использовался по умолчанию: `3`
- Что показали первые примеры retrieval:  
  На базовых запросах retrieval срабатывал ожидаемо хорошо: запросы про **DataFrame**, **loc / iloc**, **missing values** и **merge** возвращали правильные документы на первом месте. При этом на запросы про темы, которых ещё не было в основной базе знаний, качество было ниже: например, вопрос про **rolling windows** до обновления базы не имел точного источника и извлекал только частично похожие документы.

### 4.2. Контрольные запросы и оценка retrieval

- Сколько контрольных запросов использовалось: `10`
- Что считалось релевантным ответом: документ из `data/raw/`, указанный в поле `expected_sources` для каждого контрольного запроса
- Какие метрики retrieval считались: `hit@k`, `recall@k`, а также `rank_of_first_relevant` по каждому запросу
- Итоговый `hit@k`: `1.0` при `k = 3`
- Итоговый `recall@k`: `1.0` при `k = 3`
- Дополнительные метрики (если были): сохранялся `rank_of_first_relevant` для анализа качества попадания в выдаче
- Какие запросы оказались самыми простыми:  
  Наиболее простыми оказались запросы с чётко выраженной терминологией, например про **missing values**, **loc / iloc**, **DataFrame** и **read_csv**.
- Какие запросы оказались самыми проблемными:  
  Среди базовых контрольных запросов явных провалов не было, но в более свободных формулировках retrieval иногда возвращал соседние по смыслу документы. Особенно это заметно на темах, где есть семантическое пересечение, например **merge** и другие операции преобразования DataFrame.

## 7. Анализ

Выбранная база знаний оказалась удачной для учебного retrieval-сценария. Она достаточно маленькая для быстрого воспроизводимого запуска, но при этом содержит разные, хорошо различимые темы внутри одной предметной области. Это позволило подготовить понятный набор контрольных запросов и заранее определить ожидаемые релевантные документы. Выбранный способ чанкинга тоже показал себя нормально: простое разбиение по символам с overlap оказалось достаточным для коротких справочных текстов. При таких документах сложный чанкинг не был обязателен, а простой подход дал воспроизводимый и понятный результат.

Формальная оценка retrieval оказалась полезной, потому что позволила не ограничиваться визуальной проверкой примеров, а явно посчитать `hit@k` и `recall@k`. Метрики показали, что на контрольном наборе запросов retrieval работает очень хорошо. При этом сама по себе высокая метрика не означает, что любой свободно сформулированный вопрос будет обработан идеально: это стало видно на mini-RAG и на пограничных примерах. Эксперимент с `top_k` показал, что для этой базы знаний различие между `top_k=1` и `top_k=3` по retrieval-метрикам не проявилось, но для RAG более высокий `top_k` оказался полезнее, потому что даёт больше контекста.

Обновление базы знаний дало наиболее наглядственный эффект. До добавления новых документов запросы по `pivot_table`, `rolling windows` и `categorical dtype` не имели точных релевантных источников в основной базе, поэтому retrieval находил только косвенно похожие документы. После update и переиндексации система стала возвращать правильные источники, и качество ответов по этим темам заметно выросло. Наиболее показательные ошибки mini-RAG были связаны не с полной поломкой retrieval, а с тем, что в контекст попадали соседние по смыслу темы. В таких случаях extractive-ответ мог включать предложение, которое формально похоже на вопрос по словам, но не является лучшим ответом по смыслу.

Основные ограничения текущего решения связаны с учебным характером контура. Во-первых, здесь используется TF-IDF, а не плотные нейросетевые эмбеддинги. Во-вторых, mini-RAG строит ответ extractive-способом, а не через полноценную генеративную модель. В-третьих, база знаний небольшая и синтетическая, поэтому на ней легко получить хорошие метрики, но результаты нельзя автоматически переносить на более сложные реальные данные.

## 8. Итоговый вывод

Для такой учебной задачи я бы оставил в качестве базового решения retrieval-конвейер вида **чанкинг → TF-IDF-векторизация → L2-нормализация → FAISS IndexFlatIP → top-k retrieval**. Главный вывод состоит в том, что качество retrieval зависит не только от векторизации, но и от состава самой базы знаний: если нужного документа нет, то и RAG не сможет дать хороший ответ. Также стало понятно, что даже при простом mini-RAG итоговый ответ напрямую зависит от того, какие источники были извлечены на предыдущем шаге. То есть хорошее retrieval — это основа качества всего RAG-контура.
